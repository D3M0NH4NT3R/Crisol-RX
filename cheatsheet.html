El archivo crisol.json

Se crea automáticamente junto al ejecutable en el primer arranque. Se edita con cualquier editor de texto y los cambios se aplican al reiniciar la aplicación.

{
  "listen": "127.0.0.1:8723",
  "db": "",
  "org_name": "",
  "open_browser": true,
  "secure_cookies": false,
  "trust_proxy": false,
  "allowed_hosts": [],
  "allowed_ips": [],
  "tls_enabled": false,
  "cert_file": "",
  "key_file": "",
  "encrypt_db": false,
  "db_passphrase": "",
  "backup_enabled": false,
  "backup_dir": "",
  "backup_interval_hours": 24,
  "backup_keep": 7,
  "backup_passphrase": ""
}

listenstring"127.0.0.1:8723"Dirección de escucha. 127.0.0.1:8723 = solo el propio equipo. 0.0.0.0:8723 = accesible desde la red.
dbstring""Ruta del archivo SQLite. Vacío = junto al ejecutable.
org_namestring""Nombre de la organización. Aparece junto al logo y en los informes.
open_browserbooltrueAbre el navegador al arrancar. Ponlo a false en un servidor.
secure_cookiesboolfalseMarca las cookies como Secure. Actívalo si sirves por HTTPS (o tras un proxy TLS).

allowed_ipsstring[][]Lista blanca de IPs/CIDR de cliente. Vacío = sin restricción. Loopback siempre permitido.

backup_enabledboolfalseCopias automáticas: una al arrancar y otra cada N horas.
backup_dirstring""Carpeta de copias. Vacío = <carpeta de la BD>/backups.

backup_keepint7Cuántas copias se conservan (las más antiguas se borran). 0 = no rotar.
backup_passphrasestring""Passphrase para cifrar las copias. Si está vacía usa db_passphrase / CRISOL_KEY.

Flags de arranque

Opciones de línea de comandos. Tienen prioridad sobre el crisol.json.

./crisol                          # arranca según crisol.json
./crisol -addr 127.0.0.1:9000     # otra dirección/puerto
./crisol -db /ruta/otra.db        # otra base de datos
./crisol -config /ruta/otra.json  # otra configuración
./crisol -no-open                 # no abrir el navegador

# Variable de entorno: passphrase de cifrado (base + backups), no queda en disco
CRISOL_KEY=<clave> ./crisol

# Herramientas manuales de cifrado
./crisol -encrypt datos.db -out datos.db.enc
./crisol -decrypt datos.db.enc -out datos.db

Espacios, proyectos y hallazgos

El trabajo se organiza en espacios de trabajo (por cliente o equipo) y, dentro, en proyectos (cada auditoría). En cada proyecto se registran las vulnerabilidades con severidad, activo, descripción, impacto, remediación y evidencias/PoC (imágenes). Incluye etiquetas, filtros, búsqueda y acciones en lote.

CVSS, riesgo y ciclo de retest

Calculadora CVSS con vector y matriz de riesgo (probabilidad × impacto) para priorizar. Ciclo de vida claro: abierto → pendiente de retest → resuelta o riesgo aceptado. Admin, gestor y pentester marcan el retest, con contador de iteraciones. Baselines y fechas de retest/resolución para el seguimiento.

Informes

Informes por proyecto con la marca de la organización (logo y color), en el idioma del proyecto, con sello y firma verificables e informe de retest. El informe se abre con la metodología y su cobertura (si se utiliza), continúa con el alcance y los activos auditados e incluye un índice con cada hallazgo. Se genera como HTML autocontenido o PDF.

Tipo de pentest y metodología

En cada proyecto, el botón Metodología permite elegir el tipo de pentest (web, API, móvil, puesto de trabajo, red interna / AD, perímetro, Wi-Fi o cloud). Se cargan las metodologías recomendadas — OWASP WSTG, PTES, API Top 10, MASVS, NIST SP 800-115 y checklists prácticos — y cada control se marca como sin incidencias, con hallazgo o no aplica. La cobertura aparece en el informe con gráficos; es opcional. Disponible para admin, gestor y pentester.

Roles, permisos y cuentas

Cinco roles — admin, gestor, pentester, consultor y cliente. El rol define qué puede hacer cada uno; compartir un espacio solo define qué ve. El gestor administra usuarios de menor nivel, nunca a administradores. Cuentas con contraseñas fuertes, 2FA (TOTP + códigos de recuperación), gestión de sesiones y confirmación de contraseña en cada cambio relevante.

Calendario, bloc cifrado y auditoría

Calendario para planificar pentests y asignar personas, con solicitudes de cambio. Bloc de notas cifrado por espacio (con su propia clave). Registro de auditoría encadenado por hash: cada acción queda trazada, verificable y exportable (solo el admin).

Importar resultados de escáneres

Importación de Nessus, Nmap, Burp, ZAP, Nuclei, OpenVAS, Qualys, Acunetix, Semgrep, Trivy y CSV, con detección automática del formato y deduplicación de los hallazgos repetidos. El detalle está en «Escáneres compatibles».

Modo servidor en red

Para que otros equipos de la red accedan a la misma instancia.

{
  "listen": "0.0.0.0:8723"
}

El resto de equipos accede por http://<IP-del-servidor>:8723. La IP local se consulta con ipconfig (Windows) o ip a / ifconfig (Linux/macOS).

⚠️
Sin HTTPS el tráfico viaja en claro: solo es aceptable en una red de confianza, y conviene activar el cifrado de comunicaciones (siguiente sección) y cambiar antes la contraseña de admin.

Control de acceso por IP (lista blanca)

Limita quién puede entrar combinando allowed_hosts (por nombre) y allowed_ips (por dirección de cliente). Solo los equipos de la lista entran; el resto recibe 403.

{
  "listen": "0.0.0.0:8723",
  "allowed_hosts": ["crisol.miempresa.local"],
  "allowed_ips": ["192.168.1.50", "192.168.1.0/24"]
}
CampoQué hace
allowed_ipsLista blanca de IPs de cliente que pueden acceder. Acepta IPs sueltas y rangos CIDR (p. ej. 192.168.1.0/24). La IP loopback (127.0.0.1/::1) siempre se permite: el propio equipo nunca se autobloquea. Vacío = sin restricción por IP. Útil para exponer en LAN solo a equipos concretos.
allowed_hostsLista blanca por nombre de host. Se rechazan las peticiones cuyo Host no esté listado. Vacío = sin restricción por nombre.

Acceso por nombre DNS propio

Para acceder por un nombre en lugar de por IP, se añade ese nombre a allowed_hosts (p. ej. crisol.miempresa.local) y se hace que resuelva a la IP del servidor, en el DNS interno o en el fichero hosts de cada equipo cliente. El acceso pasa a ser http://crisol.miempresa.local:8723.

💡
Ambos se combinan: allowed_hosts fija el nombre y allowed_ips restringe las direcciones de origen. El loopback queda siempre permitido para administrar desde el propio servidor.

HTTPS opcional

Cifra las comunicaciones, con un certificado propio o generado automáticamente.

{
  "listen": "0.0.0.0:8723",
  "tls_enabled": true,
  "cert_file": "",
  "key_file": ""
}
EscenarioConfiguración
Certificado automáticoCon cert_file y key_file vacíos se genera uno automáticamente. El navegador avisa la primera vez (normal en red interna).
Certificado propioRutas del certificado y de su clave en cert_file y key_file.
💡
Bajo HTTPS, el acceso es por https://<IP>:8723 y las cookies se marcan seguras automáticamente.

Detrás de un proxy inverso (opcional)

Si Crisol-RX se sirve detrás de un proxy inverso, se activa trust_proxy en crisol.json para que el registro de actividad, la lista de IPs permitidas y el límite de intentos usen la IP real del visitante y no la del proxy.

{
  "secure_cookies": true,
  "trust_proxy": true
}

Importante: la IP del visitante solo se toma de las cabeceras cuando la conexión llega desde un proxy de la red local, y se usa la entrada que añade el propio proxy, de modo que un cliente no puede falsearla. El proxy debe añadir X-Forwarded-For de forma estándar; sin proxy, el valor debe quedar en false.

Configuración recomendada (red privada)

Ejemplo de crisol.json para exponer la instancia en una red interna con la mínima superficie: acceso restringido por IP/host, TLS, cifrado en reposo y copias cifradas.

Checklist operativo

  • Cortafuegos: abrir el puerto solo a la subred (o solo 443 con proxy).
  • Permisos 600 en crisol.json y el fichero de entorno; carpeta de datos restringida.
  • Cambiar la contraseña de administrador y activar 2FA.
  • Base de datos en disco local SSD (no en recursos de red/SMB).
  • Usar la unidad systemd endurecida y guardar las copias en un volumen aparte.

Acceso por certificado (mTLS) y certificados TLS

Capa de acceso previa e independiente: sin un certificado de cliente válido, la conexión se rechaza en el propio handshake TLS y ni siquiera se llega al login. Quien sí lo tiene, aún debe autenticarse con usuario, contraseña y 2FA. Todo lo emite el propio binario, sin herramientas externas.

🔑
Hay dos CAs distintas con papeles opuestos, que no deben confundirse. La CA del servidor firma el certificado del servidor (para que el navegador confíe y no muestre avisos). La CA de clientes firma la identidad de cada persona (para decidir quién puede conectar).
FicheroPara qué¿Se reparte?
server-ca.crtConfiar en el servidor (quita el aviso del navegador)Sí, la misma a TODOS los clientes (es pública)
server-ca.keyLlave que firma el certificado del servidorNo — secreta, solo en la máquina de admin
client-ca.crtVerifica a los clientes (va en client_ca_file)No — se queda en el servidor
client-ca.keyLlave que firma la identidad de cada clienteNo — secreta, offline a poder ser
usuario.p12Identidad personal de un usuario (mTLS)Solo el suyo a cada persona (único)

1 · Certificado del servidor (firmado por su CA)

El comando crea la CA del servidor si no existe y emite el certificado del servidor con los nombres/IPs de acceso. Solo se reparte server-ca.crt.

./crisol -make-server-cert -hosts "crisol.miempresa.local,10.0.0.10"
# → server-ca.crt  (instálalo como CA de confianza en TODOS los clientes)
# → server.crt / server.key  (van en cert_file / key_file)

2 · CA de clientes (una vez)

./crisol -make-client-ca -out-cert client-ca.crt -out-key client-ca.key
# client-ca.crt → se indica en client_ca_file (NO se reparte)

3 · Un certificado por persona

# repite por cada usuario
./crisol -make-client usuario1 -ca-cert client-ca.crt -ca-key client-ca.key
./crisol -make-client ana      -ca-cert client-ca.crt -ca-key client-ca.key

# empaquetar para importar en el navegador (opcional, con openssl)
openssl pkcs12 -export -legacy -inkey ana.key -in ana.crt \
  -certfile client-ca.crt -name "Crisol-RX - ana" -out ana.p12

4 · Activar en crisol.json

{
  "listen": "0.0.0.0:8723",
  "tls_enabled": true,
  "cert_file": "/opt/crisol/certs/server.crt",
  "key_file": "/opt/crisol/certs/server.key",
  "tls_hosts": ["crisol.miempresa.local", "10.0.0.10"],
  "allowed_hosts": ["crisol.miempresa.local"],
  "secure_cookies": true,
  "require_client_cert": true,
  "client_ca_file": "/opt/crisol/certs/client-ca.crt",
  "client_allow_dir": "/opt/crisol/certs/clients-allow",
  "client_blacklist_file": "/opt/crisol/certs/revoked.txt"
}

client_allow_dir es opcional: una carpeta con los .crt de los clientes permitidos. Para revocar un acceso se borra su .crt y se reinicia el servicio. Si se activa require_client_cert sin CA, el binario no arranca (protección fail-closed): nunca queda abierto por error.

🚫
Lista negra de certificados (opcional): client_blacklist_file apunta a un fichero de texto con huellas SHA-256 de certificados de cliente revocados, una por línea (admite comentarios con #). Un certificado de esa lista se rechaza siempre, aunque también figure en el allowlist, y se aplica en caliente (sin reiniciar): tanto al recargar con SIGHUP como desde Administración → Blacklist de certificados, donde un administrador puede listar, añadir y quitar huellas. La huella de un .crt se obtiene con openssl x509 -in cliente.crt -noout -fingerprint -sha256.

5 · En cada equipo cliente

  • server-ca.crt → almacén de Autoridades (Firefox) o llavero Sistema con «confiar siempre» (macOS/Windows). La misma para todos; quita el aviso.
  • su .p12 personal → almacén Personal / Sus certificados. Es lo que le deja entrar.
  • Resolver el nombre por hosts o DNS interno: 10.0.0.10 crisol.miempresa.local.

Importar en cada equipo (paso a paso)

📌
Dos importaciones por equipo: server-ca.crt como autoridad de confianza (para el candado sin aviso) y el .p12 personal en Personal / Sus certificados (para poder entrar). server-ca.key y client-ca.key nunca se tocan en el cliente.

macOS — por terminal (lo más fiable):

# confiar en el servidor (CA) para todo el equipo
sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain server-ca.crt
# identidad del usuario (pide la contraseña del .p12)
security import ana.p12 -k ~/Library/Keychains/login.keychain-db -P 'P12_PASS'

Windows — doble clic en cada fichero:

  • server-ca.crt: doble clic → Instalar → Equipo local → «Entidades de certificación raíz de confianza».
  • ana.p12: doble clic → Usuario actual → se introduce la contraseña → almacén Personal (automático). Chrome y Edge lo usan directamente.

Linux (Chrome/Chromium usan la base NSS del usuario):

# confiar en el servidor (CA) a nivel de sistema
sudo cp server-ca.crt /usr/local/share/ca-certificates/crisol-server-ca.crt && sudo update-ca-certificates
# identidad del usuario
pk12util -d sql:$HOME/.pki/nssdb -i ana.p12

Firefox (usa su propio almacén, cualquier SO):

  • server-ca.crt: Ajustes → Certificados → Ver certificados → Autoridades → Importar → se marca «confiar para identificar sitios web».
  • ana.p12: pestaña Sus certificados → Importar → contraseña del .p12.
⚠️
El .p12 se crea con openssl (único paso que aún lo usa); en macOS se añade -legacy para que el Llavero pueda leerlo:
openssl pkcs12 -export -legacy -inkey ana.key -in ana.crt -certfile client-ca.crt -out ana.p12
🚨
server-ca.key y client-ca.key son llaves maestras: con ellas se emiten certificados válidos. Requieren permisos 600, nunca se reparten y, a ser posible, se guardan offline tras emitir. Los .crt son públicos.

Cifrado de datos opcional

Con la aplicación cerrada, los datos quedan ilegibles para terceros.

{
  "encrypt_db": true,
  "db_passphrase": "una-frase-larga-y-secreta"
}
🔑
¿No aparece el archivo cifrado? Es normal: se crea al cerrar la aplicación con Ctrl-C, no al arrancar. Durante el trabajo los datos están descifrados; al cerrar ordenadamente se cifran y se borra la copia en claro.
🚨
Conviene cerrar siempre con Ctrl-C: si el proceso se interrumpe de golpe, el cifrado no se ejecuta. La passphrase debe custodiarse bien: si se pierde, los datos no se recuperan.
🛡️
Opción más segura: en lugar de escribir la passphrase en el crisol.json, se deja vacía y se pasa por variable de entorno al arrancar, sin que quede en disco:
CRISOL_KEY='tu-passphrase' ./crisol

Abrir y consultar los datos manualmente

# Descifrar (pide la passphrase o usa la variable CRISOL_KEY)
CRISOL_KEY='tu-passphrase' ./crisol -decrypt crisol.db.enc -out crisol.db

# Consultar con cualquier cliente SQLite
sqlite3 crisol.db ".tables"

# Volver a cifrar y borrar la copia en claro
CRISOL_KEY='tu-passphrase' ./crisol -encrypt crisol.db -out crisol.db.enc
rm -f crisol.db crisol.db-wal crisol.db-shm

Cambiar la passphrase

Cambiar la frase en el crisol.json no basta si ya hay datos cifrados: el archivo sigue cerrado con la frase anterior.

# Con el servidor PARADO:
# 1) Descifrar con la frase ANTIGUA
CRISOL_KEY='frase-vieja' ./crisol -decrypt crisol.db.enc -out crisol.db

# 2) Volver a cifrar con la frase NUEVA
CRISOL_KEY='frase-nueva' ./crisol -encrypt crisol.db -out crisol.db.enc

# 3) Borrar la copia en claro
rm -f crisol.db crisol.db-wal crisol.db-shm

# 4) Poner la frase NUEVA en crisol.json
💡
Si todavía no se ha generado el archivo cifrado (no se ha cerrado con Ctrl-C con el cifrado activo), basta con editar db_passphrase en el crisol.json.

Copias de seguridad automáticas

La app hace copias automáticas, cifradas con AES-256-GCM y con retención. Se configuran en crisol.json.

{
  "backup_enabled": true,
  "backup_dir": "",
  "backup_interval_hours": 24,
  "backup_keep": 7,
  "backup_passphrase": ""
}
CampoQué hace
backup_enabledtrue/false. Activa las copias automáticas.
backup_dirCarpeta de destino. Vacío = <carpeta de la BD>/backups.
backup_interval_hoursHoras entre copias. Por defecto 24, mínimo 1.
backup_keepCuántas copias conservar. Por defecto 7.
backup_passphraseSi está vacío usa db_passphrase / CRISOL_KEY. Si no hay ninguna, la copia se guarda sin cifrar y se avisa.

Restaurar una copia

Con la herramienta de descifrado incluida, indicando la passphrase de la copia:

CRISOL_KEY='tu-passphrase' ./crisol -decrypt backups/crisol-AAAAMMDD-HHMMSS.db.enc -out restaurada.db
📋
Copias cifradas de extremo a extremo: facilitan una buena práctica de respaldo y protegen los datos en reposo.

Buenas prácticas

🔑Cambiar cuanto antes la contraseña inicial de admin.
🌐Exponer la instancia a la red solo con HTTPS y en redes de confianza.
🔒Con el cifrado activo, guardar la passphrase en un gestor de contraseñas y proteger el crisol.json.
⏻Cerrar siempre con Ctrl-C para que el cifrado y la limpieza se completen.
🙈No publicar los archivos de datos, el crisol.json ni los certificados.
📦Las exportaciones de workspace contienen datos reales de clientes: deben tratarse como información sensible.

Despliegue seguro (Linux y macOS)

Para un servidor: usuario dedicado, permisos mínimos, servicio del sistema y cortafuegos. Guía completa en docs/DESPLIEGUE-SEGURO.md.

1. Usuario dedicado y permisos mínimos

# Usuario de servicio sin login (Linux)
sudo useradd --system --home /opt/crisol --shell /usr/sbin/nologin crisol
sudo chown -R crisol:crisol /opt/crisol

# Solo el servicio lee la config, la clave TLS y la base
sudo chmod 600 /opt/crisol/crisol.json crisol-key.pem crisol.db*
sudo chmod 700 /opt/crisol/backups
🔑
La passphrase no debe ir en el crisol.json: se pasa por la variable CRISOL_KEY desde el propio servicio, de modo que no queda en disco.

2. Servicio en Linux (systemd endurecido)

# /etc/systemd/system/crisol.service
[Service]
User=crisol
WorkingDirectory=/opt/crisol
ExecStart=/opt/crisol/crisol
EnvironmentFile=/etc/crisol/crisol.env   # CRISOL_KEY=...
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
RestrictAddressFamilies=AF_INET AF_INET6
SystemCallFilter=@system-service
ReadWritePaths=/opt/crisol
UMask=0077
Restart=on-failure

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now crisol
sudo journalctl -u crisol -f   # contraseña admin del 1er arranque

2b. Servicio de usuario (sin usuario dedicado)

En un equipo propio, para que se ejecute con el usuario actual, en segundo plano y al encender, sin crear un usuario del sistema, se usa un servicio --user. No necesita sudo en el día a día y los registros van al journal. Los dos bloques se copian tal cual (%h es el directorio personal). La línea EnvironmentFile lleva un - delante: es opcional y se ignora si el fichero no existe; solo hace falta si la base de datos se cifra con CRISOL_KEY.

# 1) crea la unidad de usuario (ajusta %h/crisol si tu binario está en otra carpeta)
mkdir -p ~/.config/systemd/user

Dimensionamiento del disco

El espacio en disco depende del volumen de capturas de evidencia almacenadas y de la retención de copias de seguridad:

Disco ≈ (Σ tamaño de las capturas) + (retención de backups × tamaño de la BD) + margen
💡
Cada copia de seguridad ocupa aproximadamente el tamaño de la base de datos. Se recomienda almacenar las copias en un volumen independiente, ajustar la retención con backup_keep y ejecutar VACUUM tras eliminaciones masivas para recuperar espacio.

Sistemas compatibles e instalación

Crisol-RX se distribuye como binario nativo por plataforma. Para uso en servidor se recomienda Linux (x86-64 o ARM64), con la unidad systemd endurecida y el HTTPS + acceso por certificado (mTLS) del propio binario.

Compatible con Windows (x64 / ARM64), macOS (Apple Silicon e Intel) y Linux (x64 / ARM64), con soporte ARM64 de primera clase.

Se recomienda alojar la base de datos en un disco local SSD (no en recursos de red/SMB) sobre un sistema de 64 bits, y cambiar la contraseña de administrador y activar el cifrado de datos antes de exponer la instancia.

Despliegue paso a paso en Ubuntu / Debian

Sobre la unidad systemd endurecida del kit (arranque automático, reinicio ante caídas y sandbox estricto). El binario es estático: no instala nada en el sistema.

1. Usuario de servicio y binario en /opt/crisol:

sudo useradd --system --home /opt/crisol --shell /usr/sbin/nologin crisol
sudo mkdir -p /opt/crisol && sudo cp crisol-linux-amd64 /opt/crisol/crisol
sudo chown -R crisol:crisol /opt/crisol

2. Se crea el crisol.json (con la configuración de «Servidor y red») y la passphrase se guarda en CRISOL_KEY, nunca en el fichero:

sudo install -d -m 700 /etc/crisol
echo 'CRISOL_KEY=<clave-larga-aleatoria>' | sudo tee /etc/crisol/crisol.env
sudo chmod 600 /etc/crisol/crisol.env /opt/crisol/crisol.json

3. Servicio systemd endurecido (incluido en deploy/):

sudo cp deploy/crisol.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now crisol

4. Cortafuegos (ufw) restringido a la subred:

sudo ufw allow from 192.168.1.0/24 to any port 8723 proto tcp

./crisol -make-server-cert -hosts "crisol.miempresa.local,10.0.0.10"
# luego en crisol.json: tls_enabled=true, cert_file/key_file y require_client_cert

Fragua es un binario único (sin dependencias). Se descarga el de cada sistema desde dist/ o se compila con ./build.sh. Sintaxis: ./fragua [flags].

./fragua --url https://objetivo.ejemplo   # escaneo de un activo web
./fragua --host 10.0.0.5                   # auditoría de una máquina
./fragua --version                         # ver la versión
./fragua -h                                # ayuda con todas las flags
⚠️
Uso ético: solo deben auditarse sistemas con autorización explícita.

Escaneo de puertos y servicios «por fuera» (TCP connect, estilo -Pn). Un puerto abierto es info; solo se marca vulnerabilidad ante un problema real (versión vulnerable, servicio sin auth…).

--host 10.0.0.0/24            # IP, rango CIDR o varios con comas
--targets objetivos.txt       # objetivos desde fichero (uno por línea)
--ports 22,80,443             # puertos concretos (o un rango 1-1024)
--all-ports                   # los 65535 puertos (lento)
--no-portscan                 # no escanear puertos
--scope alcance.txt           # lista blanca de hosts/IP autorizados
--deep-services               # reconocimiento PROFUNDO de servicios (sondas por protocolo)
💡
Sin --ports se escanean los 1000 puertos top de nmap. Ejemplo: ./fragua --host 10.0.0.5 --ports 1-1024.
🔬
Reconocimiento profundo (--deep-services): sondea cada servicio a nivel de protocolo y reporta lo que observa: SSH (algoritmos débiles), SMTP (STARTTLS, AUTH, VRFY), FTP (TLS), MySQL/Redis (versión), HTTP en cualquier puerto, Elasticsearch/Docker API expuestos, VNC y TLS (certificado y protocolos obsoletos). También infiere el SO por los banners (heurístico, tipo nmap -O light) y cubre cualquier puerto abierto. Incluye datastores sin auth (CouchDB, etcd, kubelet, MongoDB, LDAP), rsync y recon UDP (DNS version.bind/recursión, NTP monlist). Es activo y más lento.

Rastrea el dominio y comprueba TLS, cabeceras, configuración, XSS/SQLi reflejados, secretos en HTML/JS y análisis de JWT.

--url https://objetivo.ejemplo   # escaneo con rastreo del dominio
--max-pages 40                   # límite de páginas a rastrear
--no-crawl                       # escanear solo la URL dada
--passive                        # modo pasivo: sin sondas activas
--insecure                       # no verificar el certificado TLS

# — Analizar un JWT concreto (sin escanear) —
--jwt 'eyJhbGciOi...'            # analiza EXCLUSIVAMENTE ese token y sale
🔑
--jwt <token>: analiza un token pegado manualmente (útil porque muchos JWT solo se obtienen ya autenticado). No necesita --url/--host: decodifica, muestra los puntos débiles y el decode resaltado para la captura, y genera su fichero para importar.

Con credenciales SSH, Fragua entra «por dentro» (Linux/Windows) y enumera vías de escalada. El bastionado (hardening) se ejecuta siempre junto a las vulnerabilidades.

--ssh-user root --ssh-pass 's3cr3t'          # autenticación por contraseña
--ssh-user ops --ssh-key ~/.ssh/id_ed25519   # autenticación por clave privada
--ssh-key-pass 'passphrase'                  # passphrase si la clave está cifrada
--ssh-port 2222                              # puerto SSH distinto del 22
--ssh-agent                                  # usar ssh-agent (SSH_AUTH_SOCK)
--ssh-known-hosts ~/.ssh/known_hosts         # verificar la clave del host
--ssh-strict                                 # fallar si la clave del host no coincide

# — Escaneo profundo de credenciales (opcional, lento) —
--deep-creds                                 # caza EXHAUSTIVA de credenciales por todo el FS
--deep-creds-bin                             # además, busca secretos en binarios (muy lento)
🛡️
Bastionado incluido: ASLR, firma SMB, LLMNR, RDP/NLA, BitLocker, política de contraseñas… y localización de credenciales (imprime la ruta y enmascara el valor). Sale en un fichero -bastion aparte.
🔎
Escaneo profundo (--deep-creds): recorre todo el sistema de ficheros y los directorios de todos los usuarios, no solo el home del usuario SSH. Para una cobertura total conviene conectar como root o con sudo: un usuario sin privilegios solo ve lo que puede leer. Es lento; --deep-creds-bin añade el análisis de binarios (mucho más lento).

Windows por WinRM

Audita máquinas Windows desde dentro mediante WinRM cuando el objetivo no expone SSH. Ejecuta los mismos chequeos de solo lectura que la auditoría interna: configuración, superficie de escalada, parches, UAC/LSA/Defender/SMB, administradores locales, servicios y bastionado. Emplea las credenciales de red --user, --pass y --domain.

./fragua --host 10.0.0.5 --user Administrador --pass 'P@ss' --domain CORP   # Windows por WinRM con el 22 (SSH) cerrado
./fragua --host 10.0.0.5 --user admin-local --pass 'P@ss'                     # cuenta local: dejar --domain vacío
🪟
Activación: con --user/--pass y sin credenciales SSH (--ssh-*), prueba WinRM en 5985 (HTTP) y 5986 (HTTPS). La autenticación es NTLM, por lo que admite cuentas de dominio (CORP\usuario) y locales. Sobre HTTPS no valida el certificado del objetivo.
🔒
Requisitos: WinRM habilitado en el objetivo y una cuenta autorizada (administradores locales o grupo Remote Management Users). Opera en solo lectura: no vuelca credenciales (SAM/LSASS/NTDS), no ejecuta payloads ni realiza pass-the-hash.

Genera un JSON en formato crisol-workspace listo para Importar en Crisol-RX. Vulnerabilidades y bastionado van a dos ficheros distintos.

--out informe.json            # nombre del fichero de salida
--report md,html,csv,sarif    # informes legibles además del JSON
--name "Cliente ACME"         # nombre del workspace/proyecto
--lang both                   # informe en ES y EN (es | en | both)
📄
Dos ficheros: crisol-<host>.json (vulnerabilidades) y crisol-<host>-bastion.json (bastionado). Cada uno se importa por separado en Crisol-RX.

Ajuste de los tiempos y del ruido del escaneo.

--timeout 20      # timeout por conexión/petición (segundos)
--max-time 600    # tiempo total máximo del escaneo (segundos)
--rate 20         # máximo de peticiones web por segundo
--quiet           # sin salida en vivo, solo el resumen

Combinaciones habituales de principio a fin.

# Web + informe HTML en dos idiomas
./fragua --url https://objetivo.ejemplo --report html --lang both --out acme.json

# Reconocimiento de una subred con límite de tiempo
./fragua --host 10.0.0.0/24 --max-time 900 --report md

# Auditoría interna completa (vulns + bastionado) con informes
./fragua --host 10.0.0.5 --ssh-user ops --ssh-key ~/.ssh/id --report md,html --name "ACME infra"
📥
Después, en Crisol-RX: Importar workspace → se selecciona el .json (y el -bastion.json, si existe).

Todo esto ocurre de forma automática, sin flags: Fragua cruza y puntúa lo que encuentra para facilitar la priorización.

🎯
Confianza y menos ruido: los secretos se puntúan por entropía y patrón, se descartan los placeholders (ejemplos), y cada hallazgo lleva su nivel de confianza (alta/media/baja).
🔗
Cadenas de ataque: cruza hallazgos sueltos en rutas de escalada o pivote (p. ej. SUID + sudo + Docker → un hallazgo compuesto de mayor severidad).
🗂️
Base CVE offline: mapea versiones/banners a CVE conocidos sin conexión (Apache 2.4.49, ProFTPD, Exim, Samba, PHP/OpenSSL EOL, Jenkins, Grafana…).
🧭
Escaneo adaptativo: si detecta un stack (WordPress, phpMyAdmin, Tomcat, Drupal, Adminer…) lanza sus comprobaciones específicas.
🔑
Análisis de JWT: decodifica los tokens y detecta alg=none, cabeceras jku/jwk/kid peligrosas, secreto HS débil (fuerza bruta offline), caducidad y datos sensibles. En consola subraya los puntos débiles para la captura. Se ejecuta al encontrarlos en un escaneo o a demanda con --jwt '<token>' (sin escanear; útil para tokens que solo se obtienen ya autenticado).
🌐
Contexto: los hallazgos graves sobre una IP pública se marcan como «expuesto a Internet» para ayudar a priorizar.
🏷️
IDs estables + marcos: cada hallazgo tiene un ID estable entre escaneos (para diffing/seguimiento) y se etiqueta con su categoría OWASP Top 10 y técnica MITRE ATT&CK.
🧩
APIs y cabeceras a fondo: parsea OpenAPI/Swagger (enumera endpoints y marca los que no exigen auth), analiza la política CSP por directivas y revisa las cookies (SameSite, prefijos __Host-/__Secure-, sesión persistente).
🔭
Descubrimiento de superficie: minería del JavaScript (rutas/endpoints ocultos), descubrimiento de contenido (paneles/directorios con baseline anti-404), hostnames del certificado (SAN → alcance) y formularios sin anti-CSRF.

Enumeración masiva al estilo NetExec: barre los hosts, valida las credenciales proporcionadas e inventaría recursos y Active Directory. Es solo identificación y enumeración — no ejecuta comandos, no vuelca credenciales ni hace pass-the-hash.

--user admin             # usuario para enumerar SMB/LDAP/SSH (valida credenciales; sin fuerza bruta)
--pass 'Passw0rd!'       # contraseña de --user
--domain CORP            # dominio/workgroup (vacío = local)
--proto smb,ldap,ssh     # protocolo(s) a enumerar directo (vacío = automático según puertos)
./fragua --host 10.0.0.0/24 --user admin --pass 'P@ss' --domain CORP   # barrido automático (por puertos abiertos)
./fragua --host 10.0.0.0/24 --proto smb --no-portscan --user admin --pass 'P@ss'   # dirigido a SMB, sin escanear puertos
./fragua --host dc01 --proto ldap --user u --pass p --domain CORP   # AD en el controlador de dominio
🗄️
SMB: prueba sesión nula y GUEST, valida las credenciales, inventaría los recursos compartidos y su acceso de lectura, y detecta acceso administrativo (lectura de C$/ADMIN$ → el «Pwn3d!» de NetExec, como hallazgo). No escribe nada en el objetivo.
🧭
LDAP / Active Directory: avisa de lectura anónima del RootDSE y, con credenciales, identifica cuentas AS-REP-roasteables, Kerberoasteables (SPN), con PASSWD_NOTREQD y con delegación sin restricción. Solo detección: no pide tickets ni extrae hashes.
🔐
SSH: valida si las credenciales autentican (y marca el login de root por contraseña como grave). No ejecuta ningún comando.
🎨
Salida en vivo estilo NetExec con los colores de Fragua: PROTO  host:puerto  [+/-/*] mensaje (verde = éxito, rojo = denegado, violeta = info, verde negrita = acceso ADMIN/ROOT). Respeta --quiet y --no-color.
